# OPTICAL ARSENAL

手持ちのカメラとレンズを、オリジナルの戦術端末UIで選択・比較・紹介できる個人向けWebアプリです。React / TypeScript / Viteによる静的SPAで、アプリ実行にバックエンドは不要です。

ダークなハンガー、グリッド、機材フレーム、横方向の性能バーという一般的な視覚表現を採用しています。公式のロゴ、ゲーム固有の名称、トレースしたアイコン・機体画像・画面レイアウトは使用していません。アプリ内の機材イラストとアイコンは独自制作です。メーカー名・製品名は、ユーザー指定のサンプル機材を識別するためのテキストです。

## 機能

- CAMERA SELECT：カメラ選択、写真、ロール、説明、7項目の横バー、7項目の主要スペック。
- LENS / LOADOUT：使用カメラ選択、対応レンズのみ／全レンズの切り替え、7項目の横バー、焦点距離・開放F値・対応マウント・用途タグ。
- 機材検索、カメラ同士／レンズ同士の最大3件比較。
- カメラ・レンズの切り替えや追加パーツの着脱に合わせて、評価バーと青・赤の補正部分が約0.9秒で滑らかに変化します。詳細・比較・編成画面で共通です。OSの「動きを減らす」設定では即時表示し、PNGにはアニメーション途中の値を含めません。
- データ管理：カメラ・レンズの追加、全項目編集、削除確認、画像のアップロード・削除。
- カメラ／レンズ別のCSV出力・読み込み。テンプレートとChatGPTへの作成依頼文、読み込み内容の確認、IDによる一括追加／更新。詳細は[CSV入出力ガイド](docs/csv-import.md)を参照してください。
- 必須項目、0〜10の評価、数値・範囲・発売年の検証と、各入力欄に表示するエラー。
- localStorageにデータと画像を保存。容量不足時はフォームを保持し、保存成功として扱いません。
- 選択中のカメラ／レンズ紹介パネルをPNG出力。16:9・1:1・4:5対応。
- PC中心のレスポンシブ表示。タブレット・スマホでも閲覧・操作可能。
- カメラの評価はDETAIL・NIGHT・LATITUDE・AF・STABILITY・ENDURANCE・MOBILITYの7項目。レンズとは独立して編集でき、旧データとCSVの読み込みにも対応します。
- カメラごとに最大8個の追加パーツを登録。グリップ・マウントアダプター・その他の装備をカメラ画面、比較、PNGに表示し、CSVでも入出力できます。
- 画面上部の「項目表示」で、評価・スペックの項目名を「英語のみ」「英語＋日本語」へ切り替え。詳細・比較・編集画面・PNG出力に適用し、このブラウザに設定を保存します。初期設定は英語のみです。

初回はカメラ6台とレンズ7本を表示します。指定されたNikon Z f、Z fc、D7500、Canon EOS 5D Mark IV、SONY α7R IIIA、FUJIFILM X-T5と、5本のFマウントレンズに加えて、初期画面でレンズ選択を試せるようZマウントの2本を収録しています。写真未設定時にはロゴなしのオリジナルイラストが表示されます。デフォルトはユーザー提供の修正版CSV（2026-10-09）のスペック・名称・評価・追加パーツを採用しています。原本は[src/data/defaults](src/data/defaults)に収録しています。**0〜10の評価は主観的な参考値で、メーカー測定値ではありません。**

## 追加パーツ

対応するマウントアダプターを登録すると、MOUNT欄に追加で使えるレンズマウントを青字で追記します。FTZ II（Nikon Z）、LA-FE1（Sony E）、FR-FTX2（Fujifilm X）では「+ NIKON F」を表示し、詳細・比較・PNGへ反映します。同じマウントは重複表示せず、アダプターの削除で追記も消えます。本体のマウント値や評価補正の編集とは独立した表示です。

指定の7種類には、メーカー仕様から設定した参考補正を適用します。[補正値と調査元](docs/part-effects.md)を参照してください。STABILITYは装備時には保持の安定性も含みますが、IBISの補正段数を変更するものではありません。登録名が未対応のパーツは補正0で開始します。装備の削除で元に戻り、本体スコアは上書きされません。複数パーツの補正を合算した後、0〜10に収め、実際の増減を表示します。

ライティング装備としてGodox X2-TとTT600を登録できます。参考値はX2-Tが90 g・MOBILITY −0.3、TT600が400 g・MOBILITY −1.5です。電池の重量は含みません。WEIGHTには登録した追加重量を赤字で追記し、ADDITIONAL FUNCTIONS（追加機能）欄にはそれぞれWIRELESS FLASH（無線ストロボ使用可）・FLASH（ストロボ使用可）を青字で表示します。評価補正を変更しても機能は維持され、装備の削除で消えます。X2-TにはHIGH SPEED SYNCとTTLも表示します。TTLは対応ストロボ使用時、TT600のHSSは無線使用時に対応し、TT600自体はTTL非対応です。詳細・比較・PNGで共通の表示です。

編集画面の「X2-Tを追加」「TT600を追加」で登録でき、各パーツの「STATUS EFFECTS」から追加重量・機能も変更できます。「参考値に戻す」は評価・重量・機能をまとめて戻します。従来のグリップ・アダプターには重量の初期値を設定していないため、WEIGHTは登録した追加重量の合計を表します。必要に応じてこれらの重量や電池込みの重量を入力してください。CSVでも同じ設定を読み書きできます。

「データ管理」→「カメラ」→対象カメラの「編集」で、ADDITIONAL PARTS欄から種類と名称を登録します。名称は1行64文字まで、最大8個です。装着したパーツの補正を本体の評価に加え、増加分を青、減少分を赤の数値とバーで表示します。カメラ詳細・比較・PNGの値は共通です。「STATUS EFFECTS」を開くとパーツごとの補正（−10〜+10）を編集でき、「参考値に戻す」で自動補正に戻ります。「項目表示」の切り替えはパーツ欄にも適用します。

追加パーツ欄のない旧保存データは、同じID・機材名の標準カメラにグリップ・アダプターの初期装備を読み込みます。今回のライティングは、同じID・機材名の4台へ空きスロットの範囲で一度だけ追加します。登録済みの同種装備は重複追加せず、既存の評価・写真・パーツ設定を保持します。保存後に削除したライティングは再追加しません。元の保存データは保存操作まで変更しません。

## 装備の付け替えと編成

カメラ選択画面の「装備を付け替える」を開き、装備をタップして装着・解除します。変更は即時保存され、評価・重量・対応マウント・追加機能へ反映します。外したパーツは再装着候補に残ります。既知のグリップ・アダプター・X2-Tは対応するカメラの候補に表示し、独自パーツはデータ管理から登録できます。1台あたり8枠です。装着中のアダプターで対応するレンズも、レンズ選択画面の候補に含めます。

レンズ選択後に「この組み合わせで編成へ」を押すと、そのカメラ・レンズをメイン機に設定して編成画面を開きます。サイドメニューの「SQUADRON / SORTIE」からも開けます。「僚機を追加」で複数台を登録し、それぞれカメラ・レンズを変更できます。登録カメラの台数まで追加でき、同じカメラ・レンズの重複配置を防ぎます。装備は各カメラと共有し、編成画面でも付け替えられます。

全機のカメラとレンズを選び、対応マウントが一致するとREADY（編成完了）を表示します。アダプターを外して接続が合わなくなった場合は、選択を残して確認表示を出します。編成はブラウザに保存され、再読み込み後はサイドメニューから再表示できます。機材削除時はその参照を解除します。CSVの対象は機材と装着中パーツで、編成・再装着候補の一覧は含みません。

### 設計上の選択

- 推奨構成の例から、MVPで必要なまとまりに整理しました。管理画面のカメラ／レンズ編集は共通コンポーネントを用い、同じ検証を使います。
- `mount`はCamera直下に持たせ、specs内へ二重管理しません。対応はマウント名の厳密一致です。`Nikon Z`、`Nikon F`等の表記を統一してください。複数マウント・タグはカンマ区切りで入力できます。
- `AdapterRule`を互換性関数のオプションに分離しています。MVPはアダプターを自動的に互換と扱いません。将来はAF・絞り制御・センサー範囲を含む互換性ルールへ拡張できます。
- specsは単位付き文字列を許可します。重量・解像度・連写速度・焦点距離・F値は正の数値と範囲を検証します。例：`710 g`、`24.5 MP`、`約 14 コマ/秒`、`24–70 mm`、`f/3.5–4.5`。評価は数値型です。
- 選択対象が削除・絞り込みによって消えた場合は、現在の一覧の先頭へフォールバックします。表示データが空でも自動的なサンプル再投入はしません。
- PNGは、現在選択中の機材・使用ボディ・説明・性能・スペックを固定サイズの共通パネルで描画します。SNS向けに操作ボタン・検索欄・全機材リスト・比較ダイアログは含めません。16:9は左右レイアウト、1:1と4:5は上下レイアウトへ切り替えます。
- ダイアログはブラウザ標準の`dialog`を使用し、フォーカス制御とEscapeキーを利用します。画像やチャートに代替テキスト・meter属性を付けています。

## セットアップ

Node.js **22.12以上**を推奨します（Viteの要件：20.19以上または22.12以上。本環境では24.19.0で検証）。npmを利用します。

```bash
cd camera-hangar-app
npm ci
npm run dev
```

表示されたローカルURL（通常 `http://localhost:5173`）を開いてください。`dev`は開発環境のプレビュー用に`0.0.0.0`へバインドします。自身のPCだけに限定する場合は次を使用してください。

```bash
npm run dev -- --host 127.0.0.1
```

本番公開ブランチは **develop**、手動確認用ブランチは **pre-develop** です。新規Gitリポジトリを作る場合も次のようにしてください。

```bash
git init -b develop
```

## テスト手順

最初にPlaywright用ブラウザをインストールしてください。

```bash
npm ci
npx playwright install chromium
npm test
npm run test:e2e
```

LinuxのCI等でOS依存パッケージも必要な場合は `npx playwright install --with-deps chromium` を利用できます。本環境のようにChromiumが既にある場合は次も利用できます。

```bash
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run test:e2e
```

E2EはViteを4173ポートで自動起動します。非CI環境では同じURLで起動済みのサーバーを再利用します。失敗時のトレースは`test-results/`へ保存します。`.github/workflows/ci.yml`はpre-develop・developへのpush・PRで同じ確認を行います。pre-developへのpushでは、すべての確認に合格したビルドをGitHub Pagesへ公開します。

テストは表示状態だけでなく実際のデータも確認します。

- UT：評価→バー幅、互換性と将来のアダプター規則、フォーム検証、保存・読み込み、壊れた保存データ・容量不足、出力サイズ、画像形式・容量制限。
- IT：カメラ選択→レンズ絞り込み、フォームエラー→保存→localStorage、保存失敗時のフォーム保持、複数マウント・タグの手入力。
- E2E：初回サンプル、選択切替、カメラ／レンズ両方の追加・編集・削除と再読み込み、非互換表示、画像アップロード、比較、画面幅、空データの維持。
- PNGのE2E：両画面×3比率について本物のダウンロードを取得。PNGシグネチャ・ピクセル寸法・ブラウザでのデコードを検査します。

TDDを意識し、ドメインの期待値とUIフローのテストを先に記述し、失敗を確認してUIを実装しました。実装後に見つけた複数マウント入力・壊れた保存データの上書き・スキーマ検査の問題も、再現テストが失敗することを確認してから修正しています。jsdomの`dialog`は最小のテスト代替実装を使い、ブラウザ側の操作はPlaywrightで確認しています。

## ビルド・静的ホスティング

```bash
npm run build

```

生成された`dist/`を静的ホスティングへ置くだけで利用できます。Viteの`base: './'`を設定しており、サブディレクトリへの配置も考慮しています。画面切替はクライアント内で行うため、SPAの履歴ルーティング用リライトは不要です。ビルド結果を`file://`で直接開かず、HTTPサーバーで配信してください。Vercel用のビルド設定は`vercel.json`に記載しています。

## GitHub Pagesで確認してから本番公開

確認用URL： **https://ketochiko-ops.github.io/camera-hangar-app/**

1. 初回のみ、GitHubの[Settings → Pages](https://github.com/ketochiko-ops/camera-hangar-app/settings/pages)でSourceを **GitHub Actions** にします。
2. 作業ブランチの変更を`pre-develop`へ取り込み、pushします。GitHub ActionsがUT・IT・ビルド・E2Eを実行し、合格後に確認用サイトを更新します。失敗した場合、以前の確認用サイトを保持します。
3. PC・スマートフォン・タブレットから確認用URLを開き、表示・操作・CSV入出力・PNG出力を手動確認します。
4. 確認できた変更について`pre-develop → develop`のPRを作成し、チェック通過後にマージします。Vercelの本番サイトが更新されます。

初回設定後にPages公開が失敗した場合は、[Actions](https://github.com/ketochiko-ops/camera-hangar-app/actions)で該当実行の「Re-run failed jobs」を選択してください。ワークフローをdevelopにも取り込んだ後は、手動実行のブランチにpre-developを指定して再公開することもできます。

GitHub Pagesの`github-pages`環境にデプロイ対象ブランチの制限がある場合は、[Settings → Environments](https://github.com/ketochiko-ops/camera-hangar-app/settings/environments)でpre-developを許可してください。SourceをActionsにした場合、Pagesの公開元はワークフローの条件でpre-developに限定しています。

`vercel.json`の`git.deploymentEnabled`で、developだけVercelのGit自動デプロイを許可しています。pre-developや作業ブランチのpushは、VercelのPreviewビルドを起動しません。GitHub Pagesのビルド・配信にはGitHub側の利用枠が適用され、Vercelの利用枠は使いません。

登録機材・写真はブラウザとオリジンごとのlocalStorageへ保存されます。確認用サイトとVercel本番サイト、PCとスマートフォンの間でデータは共有されません。機材の移動にはCSVを利用できますが、写真はCSVに含まれません。

## Vercelでの自動デプロイ

既存プロジェクト`camera-hangar-app`を使用します。接続先は`ketochiko-ops/camera-hangar-app`です。

| 設定 | 値 |
| --- | --- |
| Production Branch | `develop` |
| Framework Preset | Vite |
| Root Directory | リポジトリ直下 |
| Install Command | `npm ci` |
| Build Command | `npm run build` |
| Output Directory | `dist` |
| Node.js | 24.x |
| 環境変数 | この静的アプリでは不要 |

Vercelの[Settings → Environments](https://vercel.com/ketochiko-ops-projects/camera-hangar-app/settings/environments)でProductionのBranch Trackingを`develop`へ設定済みです。PRを`develop`へマージすると本番が更新されます。直接`develop`にpushした場合も起動します。GitHub ActionsはUT・IT・E2E・ビルド検査を担当し、VercelはGit連携でデプロイします。CIにVercelのトークンを置く必要はありません。

テスト通過をマージの条件にする場合は、GitHubの`develop`ブランチルールで`verify`チェックを必須にしてください。VercelのGit連携だけではGitHub Actionsの完了を待たないため、本番更新をテスト通過後に限定したい場合は、このブランチルールまたはVercel Deployment Checksを追加します。

本番URL： **https://camera-hangar-app.vercel.app**

VercelのProductionドメインを利用します。アップロード写真と登録機材は閲覧者ごとのlocalStorageに保持され、Vercelへ送信されません。ローカルと本番は別オリジンなのでデータは共有されません。

## データ保存

保存キーは `optical-arsenal:inventory:v1`、JSON構造は `{ version: 1, cameras: [...], lenses: [...] }` です。初回サンプルはキーがない場合だけ表示し、最初の追加・編集・削除操作で全データを保存します。空の保存データは空のまま維持します。

写真はブラウザ内で長辺1200px以下に縮小し、WebP（品質0.82、非対応ブラウザではCanvasのフォールバック）へ再エンコードしてdata URLとして保存します。透明背景は維持します。対応する入力はJPEG・PNG・WebP、1ファイル10MiB以下です。外部へ写真を送信せず、元画像のメタデータは引き継ぎません。

保存容量はブラウザによって異なります（localStorageは数MiB程度が一般的）。data URLは元のバイナリより大きくなり、多数の写真では上限に達します。保存エラーを表示し、未保存のフォームを残します。アップロード処理中は保存を無効化します。

保存範囲はブラウザ・プロファイル・オリジン単位です。ポート／ドメインの変更、別ブラウザ、プライベートブラウズでは別データになります。ブラウザのサイトデータ削除で失われます。複数タブで同時編集した場合の競合解決は未実装で、最後に保存したデータが優先されます。

読み込みエラー時はサンプルで上書きせず、元データを保持して追加保存も停止します。復旧する場合はブラウザ開発者ツールで該当キーの内容をバックアップしてから、JSONを修復するかキーを削除し、再読み込みしてください。キーを削除すると保存機材は失われ、サンプル表示へ戻ります。

保存を`InventoryRepository`に閉じ込めています。IndexedDB移行時はリポジトリとProviderのload/saveを非同期化し、画像をBlobへ切り出せます。機材UI・互換性・検証・出力のロジックを変更する必要はありません。

## PNG出力の制約

| 比率 | ピクセル寸法 |
| ---- | ------------ |
| 16:9 | 1600 × 900   |
| 1:1  | 1200 × 1200  |
| 4:5  | 1200 × 1500  |

出力中に選択が変わっても、クリック時点のデータをスナップショットとして使用します。画像とフォントの準備完了後に生成します。出力ライブラリは遅延ロードされます。

- ブラウザのSVG foreignObject / Canvas実装に依存します。Chromiumで検証済みです。Firefox・Safariの実機検証は今後の課題です。
- OS標準フォントを使うため、OS間で日本語の字形や折り返し位置は多少変わります。
- 極端に長い名前・スペック・説明では固定サイズに収まらず、折り返しや切れが起こる可能性があります。SNS用には簡潔な説明を推奨します。入力文字数には上限を設けています。
- アップロードした透明画像はそのまま表示します。背景除去や切り抜き、画像の回転・位置編集は未実装です。
- 外部画像URLは入力させず、ローカル画像のみを使用することでCORSによる出力失敗を避けています。
- データ管理・比較ダイアログの画像出力、全機材リストの長いスクリーンショット出力は対象外です。
